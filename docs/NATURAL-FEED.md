# 🍃 Natural Feed — Лента по популярности без ИИ-профилирования (ТЗ)

> **Название:** Natural Feed 🍃
>
> **Что это:** Лента лучших и новых постов от сообщества, ранжированная по **системной популярности** (лайки, комментарии, сохранения) — **без персонального ИИ-профилирования**. Пользователь видит посты **только от своих подписок, сообществ и друзей**.
>
> **Текст для пользователя (EN):** Top and newest posts from the whole community, ranked without personal AI profiling.
> **Текст для пользователя (RU):** Лучшие и новые посты от всего сообщества, отранжированные без персонального ИИ-профилирования.
>
> **Зачем нужна:** DSA Art. 27 **ОБЯЗЫВАЕТ** предоставить альтернативу рекомендательной системе, которая **не основана на профилировании**. Natural Feed — это та самая альтернатива. Ранжирование по популярности (одинаковые метрики для ВСЕХ) ≠ профилирование (индивидуальный подбор на основе анализа поведения).
>
> **Когда реализовать:** MVP (v1.0) — одновременно со Smart Feed. По закону обязательна.

## 1. Принцип работы

```
Два фактора ранжирования:
  1. Popularity Score — системная популярность (лайки, комменты, сохранения)
  2. Freshness — свежесть поста (новые получают гарантированные слоты)

Нет AI.              Нет embeddings.        Нет весов W1–W12.
Нет профилирования.  Нет анализа поведения. Нет персонализации.

Popularity Score — одинаковый для ВСЕХ пользователей (системная метрика).
Область видимости — ТОЛЬКО подписки, сообщества и друзья пользователя.
Свои посты — НЕ показываются (пользователь не видит себя в ленте).
```

Natural Feed показывает посты от **подписок, сообществ и друзей** пользователя, ранжированные по **системной популярности**. Это НЕ персонализация, потому что:
- **Popularity Score** — одинаковая формула для всех, не зависит от поведения конкретного пользователя
- **Область контента** определяется только **явными действиями** пользователя (подписался, вступил в сообщество, добавил в друзья) — платформа **ничего за него не решает**

### Что определяет порядок

| Фактор | Влияет на порядок? | Как |
|---|---|---|
| **Popularity Score** (лайки, комменты, сохранения) | ✅ **Основной фактор** | Посты с большим engagement выше |
| **Свежесть поста** (`created_at`) | ✅ **Вторичный фактор** | Новые посты (< 2ч) получают гарантированные слоты |
| Интересы пользователя | ❌ Нет | — |
| Dwell time | ❌ Нет | — |
| Личное поведение | ❌ Нет | — |
| Язык | ✅ **Фильтруется** | По настройкам пользователя, НЕ по поведению |

## 3. Источники контента (только подписки)

> **Ключевой принцип:** Пользователь видит посты **только от тех, на кого он подписан**, сообществ, **в которых он состоит**, или друзей. Платформа **ничего за него не решает** и **не профилирует**.

| # | Источник | Условие | Примечание |
|---|---|---|---|
| 1 | **Посты от подписок** | Пользователь подписан на автора (`follows`) | Основной источник |
| 2 | **Посты из сообществ** | Пользователь — участник сообщества (`community_members`) | Включая посты от незнакомых участников |
| 3 | **Посты от друзей** | Взаимная подписка (`follows` в обе стороны) | Приоритет не повышается (нет профилирования) |
| 4 | **Публичные посты** из подписок/сообществ | `visibility = 'public'` от авторов из п.1–3 | — |
| 5 | **Приватные посты** от подписок | `visibility = 'followers'` + пользователь подписан | — |

### Чего Natural Feed НЕ показывает

| ❌ Не показываем | Почему |
|---|---|
| **Свои посты** | Пользователь НЕ видит себя в своей ленте (для своих постов есть профиль) |
| Посты от незнакомых пользователей (вне подписок/сообществ) | Платформа не решает за пользователя, что ему смотреть |
| Посты от заблокированных | Фильтр безопасности |
| Удалённые / на модерации | Фильтр безопасности |

## 5. Алгоритм Popularity Score

### Принцип

Popularity Score — это **системная метрика**, одинаковая для ВСЕХ пользователей. Она определяется **engagement** поста (лайки, комментарии, сохранения, репосты) и **свежестью**. Это **не профилирование** — формула не зависит от поведения конкретного пользователя.

### Формула Popularity Score

```typescript
function calcPopularityScore(post: Post): number {
  // 1. Базовый engagement (за последние 72 часа)
  const engagementScore =
    post.likes_count    * 1.0 +     // Лайк — базовая единица
    post.comments_count * 2.0 +     // Комментарий ценнее лайка (вовлечённость)
    post.saves_count    * 3.0 +     // Сохранение — самая ценная реакция
    post.shares_count   * 2.5;      // Репост — высокая ценность

  // 2. Нормализация по подписчикам автора (чтобы маленькие аккаунты не проигрывали)
  const authorFollowers = Math.max(post.author.followers_count, 1);
  const engagementRate = engagementScore / Math.sqrt(authorFollowers);

  // 3. Time Decay — свежесть (24-часовой полураспад)
  const hoursAgo = (Date.now() - post.created_at.getTime()) / (1000 * 60 * 60);
  const timeDecay = Math.exp(-0.693 * hoursAgo / 24);
  // 0ч → 1.0, 24ч → 0.5, 48ч → 0.25, 72ч → 0.125

  // 4. Итоговый Score
  return engagementRate * timeDecay;
}
```

### Веса engagement

| Действие | Вес | Почему |
|---|---|---|
| 👍 Лайк | 1.0 | Базовая единица |
| 💬 Комментарий | 2.0 | Требует усилий — пользователь вовлечён |
| 🔖 Сохранение | 3.0 | Самое ценное — пользователь хочет вернуться |
| 🔄 Репост / Поделиться | 2.5 | Пользователь рекомендует другим |

### Нормализация по подписчикам

> **Зачем:** Без нормализации пост от аккаунта с 10 000 подписчиков (получивший 100 лайков) всегда будет выше поста от аккаунта с 50 подписчиков (получившего 30 лайков). Но 30/50 = 60% engagement rate vs 100/10000 = 1% — маленький аккаунт реально интереснее.

```
engagementRate = engagementScore / √(followers_count)
```

Используем **квадратный корень** (не линейное деление), чтобы крупные аккаунты всё ещё имели преимущество, но не подавляли маленькие полностью.

| Подписчики | Лайки | Raw Score | √followers | Rate |
|---|---|---|---|---|
| 50 | 30 | 30 | 7.07 | **4.24** |
| 500 | 100 | 100 | 22.36 | **4.47** |
| 10 000 | 100 | 100 | 100 | **1.00** |
| 10 000 | 500 | 500 | 100 | **5.00** |

### Защита от накрутки

| Правило | Описание |
|---|---|
| Только уникальные пользователи | Повторные лайки/комменты от одного пользователя не считаются |
| Аккаунты < 24 часов | Лайки от свежезарегистрированных аккаунтов **НЕ** считаются |
| Лимит по IP | Более 50 лайков от одного IP за час → все обнуляются |
| Самолайки | Автор не может лайкнуть свой пост (или лайк не влияет на Score) |

### Пересчёт Popularity Score

| Параметр | Значение |
|---|---|
| **Когда пересчитывать** | При каждом новом лайке/комменте/сохранении (инкрементально) |
| **Полный пересчёт** | Каждые 15 минут (cron job) для учёта time decay |
| **Хранение** | Колонка `popularity_score NUMERIC` в таблице `posts` |
| **Индекс** | `CREATE INDEX idx_posts_popularity ON posts (popularity_score DESC)` |

## 6. Слоты для нового контента (New Content Slots)

### Проблема

Если ранжировать только по популярности, новые посты (< 1 часа, ещё без лайков) **никогда не попадут наверх**. Они утонут внизу, не получат engagement и не станут популярными. Это «ловушка курицы и яйца».

### Решение: Гарантированные слоты для свежих постов

```
Каждый 10-й слот в ленте = НОВЫЙ ПОСТ (< 2 часов, без минимального engagement).
Внутри этих слотов — сортировка по created_at DESC (самые свежие первые).
```

### Как это работает

```
┌──────────────────────────────────────────────────┐
│    [Smart Feed ✨]    [Natural Feed 🍃] ← АКТИВЕН│
├──────────────────────────────────────────────────┤
│  1. 🔥 Популярный пост (Score: 45.2)             │
│  2. 🔥 Популярный пост (Score: 38.1)             │
│  3. 🔥 Популярный пост (Score: 33.7)             │
│  ...                                              │
│  9. 🔥 Популярный пост (Score: 12.4)             │
│ 10. 🆕 НОВЫЙ пост от @friend (5 мин назад)       │ ← New Content Slot
│ 11. 🔥 Популярный пост (Score: 11.8)             │
│  ...                                              │
│ 19. 🔥 Популярный пост (Score: 5.3)              │
│ 20. 🆕 НОВЫЙ пост из сообщества (45 мин назад)   │ ← New Content Slot
│  ...                                              │
└──────────────────────────────────────────────────┘
```

### Правила New Content Slots

| Правило | Значение |
|---|---|
| **Позиция** | Каждый 10-й слот (позиции 10, 20, 30, ...) |
| **Возраст поста** | < 2 часов с момента публикации |
| **Сортировка внутри слотов** | По `created_at DESC` (самые свежие первые) |
| **Если нет новых постов** | Слот занимается следующим по популярности постом (без пустых дыр) |
| **Дедупликация** | Если новый пост уже попал в основную ленту по популярности → не дублировать в слоте |

### Зачем это нужно

| Без New Content Slots | С New Content Slots |
|---|---|
| Новые посты не получают просмотров | Каждый новый пост получает минимум 1 показ в слоте |
| Только уже популярные посты растут | Органическое продвижение: свежий контент → слот → лайки → попадание в основную ленту |
| «Богатые богатеют» | Справедливый шанс для всех авторов |

> **Юридически:** New Content Slots — это **не персонализация** (одинаковое правило для всех). Это **поддержка свежего контента** — аналог того, как газета ставит свежие новости на первую полосу.

## 7. Системные уведомления в ленте

### Что это

Системные посты (`system_post`) — это карточки от платформы, которые информируют пользователя о событиях в его подписках и сообществах.

### Типы системных постов

| # | Тип | Текст (EN) | Текст (RU) | Ключ перевода | Когда показывать |
|---|---|---|---|---|---|
| 1 | **Новая дискуссия** | 💬 New discussion in {community}: "{title}" | 💬 Новая дискуссия в {community}: «{title}» | `system_new_discussion` | Когда в сообществе пользователя создана дискуссия |
| 2 | **Популярная тема** | 🔥 Trending in {community}: "{title}" | 🔥 Популярно в {community}: «{title}» | `system_trending_discussion` | Когда дискуссия в сообществе набрала > 10 комментов за 24ч |
| 3 | **Друг присоединился** | 👋 Your friend @{username} joined {community} | 👋 Ваш друг @{username} присоединился к {community} | `system_friend_joined` | Друг вступил в сообщество, в котором состоит пользователь |
| 4 | **Новый блог-пост** | 📝 New article from @{username}: "{title}" | 📝 Новая статья от @{username}: «{title}» | `system_new_blog` | Когда блогер из подписок опубликовал статью |

### Правила показа системных постов

| Правило | Значение |
|---|---|
| **Частота** | Максимум 1 системный пост на 15 обычных постов |
| **Дедупликация** | Одно и то же событие показывается **один раз** |
| **Приоритет** | Системные посты НЕ вытесняют обычные — они вставляются в отдельные позиции |
| **Отключение** | Пользователь может отключить системные посты в Settings → Feed & Content |

## 8. Дедупликация и защита от повторов

### Проблема

Пост может попасть в ленту из нескольких источников: автор в подписках И пост в сообществе. Или пост достаточно популярный для основной ленты И достаточно свежий для New Content Slot. Пользователь не должен видеть один пост дважды.

### Правила дедупликации

| # | Правило | Реализация |
|---|---|---|
| 1 | **Один пост = одно показание** | `DISTINCT ON (p.id)` в SQL (или дедупликация на бэкенде) |
| 2 | **New Content Slot vs основная лента** | Если пост уже в основной ленте (по Score) → НЕ показывать в New Content Slot |
| 3 | **Сессионная дедупликация** | Бэкенд хранит `Set<post_id>` для текущей сессии. Уже отданные посты не отдаются повторно |
| 4 | **Кросс-источник** | Пост от @anna (подписка) + пост @anna в сообществе → показать ОДИН РАЗ (тот, что выше по Score) |

### Реализация

```typescript
// На бэкенде: при формировании страницы ленты
const seenPostIds = new Set<string>(); // Хранится в Redis или в запросе

function addToFeed(post: Post): boolean {
  if (seenPostIds.has(post.id)) return false; // Уже показан
  seenPostIds.add(post.id);
  return true;
}
```

## 9. Фильтры (что НЕ показываем)

Даже в ленте по популярности есть **фильтры безопасности**. Это **НЕ персонализация** — это **исключение контента**, который пользователь не должен видеть.

| # | Фильтр | Причина | Закон / Правило |
|---|---|---|---|
| 1 | **Свои посты** (`author_id = current_user`) | Пользователь НЕ видит себя в ленте | UX-правило (свои посты — в профиле) |
| 2 | Удалённые посты (`status = 'deleted'`) | Автор или модератор удалил | — |
| 3 | Посты на модерации (`ai_moderation_status = 'auto_removed'`) | AI-модерация убрала | DSA Art. 14 |
| 4 | Посты от заблокированных (`user_blocks`) | Пользователь заблокировал автора | Apple §1.2, DSA Art. 16 |
| 5 | Посты помеченные «Не интересно» (`not_interested`) | Пользователь нажал «Not interested» | DSA Art. 27 |
| 6 | Скрытые посты (`user_hidden_posts`) | Пользователь нажал «Hide this post» | DSA Art. 27 |
| 7 | Посты от restricted-аккаунтов (`author.status = 'restricted'`) | Аккаунт ограничен модерацией | DSA Art. 14 |
| 8 | Посты вне подписок/сообществ | Автор не в подписках и не в сообществе пользователя | Принцип Natural Feed |

### 9.1 Свои посты — НЕ показываем

> **Правило:** Пользователь **НЕ видит свои собственные посты** в Natural Feed.

| Аспект | Описание |
|---|---|
| **Почему** | Лента — это контент от **других**. Свои посты пользователь видит в своём профиле |
| **Как** | `AND p.author_id != :current_user` в SQL |
| **Smart Feed** | Свои посты тоже могут не показываться (опционально), но в Natural Feed это **обязательно** |
| **Уведомления** | Пользователь узнаёт об engagement своих постов через push-уведомления и вкладку Activity |

### 9.2 Языковой фильтр

> **Проблема:** Если показывать ВСЕ языки, американский пользователь увидит посты на японском, китайском, арабском — это «винегрет», а не лента. Фильтруем по **настройке пользователя**, а не по его поведению.

**Как определяется язык:**

| # | Источник | Приоритет | Пример |
|---|---|---|---|
| 1 | **Ручная настройка** (Settings → Feed & Content → Content languages) | Высший | Пользователь выбрал EN + RU |
| 2 | **Язык устройства** (из HTTP-заголовка `Accept-Language`) | Если ручная настройка не задана | `en-US`, `ru-RU` |
| 3 | **Регион регистрации** (из GeoIP при регистрации) | Fallback, если 1 и 2 не определили | US → EN |

**Правила языкового фильтра:**

| Правило | Описание |
|---|---|
| Фильтр по **настройкам**, а не по поведению | ✅ Это НЕ профилирование — пользователь сам выбирает языки |
| По умолчанию = язык устройства | Если юзер не менял настройки, показываем контент на языке его устройства |
| Юзер МОЖЕТ добавить языки | В Settings → Content languages можно добавить любые языки |
| Юзер МОЖЕТ выбрать «All languages» | Возможность отключить языковой фильтр полностью |
| Юридически безопасно | DSA Art. 27 запрещает **профилирование** (анализ поведения), а не **пользовательские настройки** |

### 9.3 Гендерный фильтр

> **В Natural Feed гендерный фильтр ❌ НЕ используется.**

| Аспект | Описание |
|---|---|
| **Почему нет** | Фильтрация по полу = персонализация на основе профиля = **профилирование** (GDPR Art. 4(4)) |
| **Где используется** | Только в **Smart Feed** (W1 — Interests) |
| **Исключение** | Авторская настройка видимости (`visibility = 'women_only'` / `'men_only'`) — допустимо, это решение автора, не платформы |

### 9.4 Защита от спама бизнес-контента (Anti-Flood Guard)

> **Проблема:** Если 10 бизнес-аккаунтов публикуют посты быстрее обычных пользователей И получают лайки от клиентов, лента превращается в рекламную доску.

**Решение: Anti-Flood Guard**

| Правило | Описание |
|---|---|
| **Макс 3 бизнес-поста подряд** | Если после ранжирования идут 4+ бизнес-поста подряд → 4-й и далее сдвигаются за следующий не-бизнес пост |
| **Не ранжирование** | Одинаковое правило для ВСЕХ пользователей |
| **Закон** | DSA Art. 14 — защита от спама |

**Пример:**

```
По популярности:                С Anti-Flood Guard:
1. 🏢 Бизнес (Score: 40)       1. 🏢 Бизнес (Score: 40)
2. 🏢 Бизнес (Score: 38)       2. 🏢 Бизнес (Score: 38)
3. 🏢 Бизнес (Score: 35)       3. 🏢 Бизнес (Score: 35)
4. 🏢 Бизнес (Score: 33) ←     4. 📝 Пост (Score: 30) ← поднят
5. 🏢 Бизнес (Score: 31) ←     5. 🏢 Бизнес (Score: 33) ← сдвинут
6. 📝 Пост (Score: 30)         6. 🏢 Бизнес (Score: 31) ← сдвинут
7. 📝 Пост (Score: 25)         7. 📝 Пост (Score: 25)
```

## 10. SQL-запрос

### Основной запрос Natural Feed (Popularity Ranking)

```sql
-- Шаг 1: Получить посты из подписок/сообществ, отсортированные по Popularity Score
SELECT p.*,
       u.username AS author_username,
       u.avatar_url AS author_avatar,
       u.is_business AS author_is_business,
       p.popularity_score
FROM posts p
JOIN users u ON u.id = p.author_id
WHERE p.status = 'published'
  -- 1. НЕ свои посты
  AND p.author_id != :current_user
  -- 2. Не удалённые модерацией
  AND p.ai_moderation_status != 'auto_removed'
  -- 3. Не от заблокированных пользователей
  AND p.author_id NOT IN (
    SELECT blocked_id FROM user_blocks WHERE user_id = :current_user
  )
  -- 4. Не скрытые пользователем
  AND p.id NOT IN (
    SELECT post_id FROM user_hidden_posts WHERE user_id = :current_user
  )
  -- 5. Не помеченные «не интересно»
  AND p.id NOT IN (
    SELECT post_id FROM user_not_interested WHERE user_id = :current_user
  )
  -- 6. Не от restricted-аккаунтов
  AND u.status != 'restricted'
  -- 7. ТОЛЬКО из подписок, сообществ и друзей
  AND (
    -- Автор в подписках
    p.author_id IN (
      SELECT following_id FROM follows WHERE follower_id = :current_user
    )
    -- ИЛИ пост из сообщества пользователя
    OR p.community_id IN (
      SELECT community_id FROM community_members WHERE user_id = :current_user
    )
  )
  -- 8. Видимость
  AND (
    p.visibility = 'public'
    OR (p.visibility = 'followers' AND p.author_id IN (
      SELECT following_id FROM follows WHERE follower_id = :current_user
    ))
    OR (p.visibility = 'community' AND p.community_id IN (
      SELECT community_id FROM community_members WHERE user_id = :current_user
    ))
  )
  -- 9. Языковой фильтр
  AND (
    NOT EXISTS (SELECT 1 FROM user_content_languages WHERE user_id = :current_user)
    OR p.language IN (
      SELECT language FROM user_content_languages WHERE user_id = :current_user
    )
    OR p.language IS NULL
  )
  -- 10. Не старше 14 дней
  AND p.created_at > NOW() - INTERVAL '14 days'
ORDER BY p.popularity_score DESC, p.created_at DESC
LIMIT :page_size;
```


## 15. Юридический статус

### Почему Natural Feed обязательна

| Закон | Статья | Требование |
|---|---|---|
| **DSA** | Art. 27 | Платформы с рекомендательными системами **ОБЯЗАНЫ** предоставить хотя бы **одну альтернативу**, не основанную на профилировании |
| **EU AI Act** | Art. 50 | Пользователь должен знать, когда контент ранжируется AI. Natural Feed = режим **без AI** |
| **GDPR** | Art. 22 | Право не подчиняться автоматизированным решениям. Natural Feed = отключение персональной автоматизации |

### Почему Popularity Score ≠ профилирование

| Аспект | Профилирование (запрещено в Natural Feed) | Popularity Score (✅ допустимо) |
|---|---|---|
| **Зависит от пользователя?** | ✅ Да — анализ поведения конкретного юзера | ❌ Нет — одинаковый Score для ВСЕХ |
| **Персонализирован?** | ✅ Каждый видит разный порядок | ❌ Все видят одинаковый Score (в пределах подписок) |
| **GDPR Art. 4(4)** | Подпадает под определение «профилирование» | Не подпадает — нет оценки личных аспектов |
| **Аналог** | YouTube: «рекомендуемое для вас» | Reddit: сортировка по upvotes (r/popular) |

### Почему «только подписки» ≠ профилирование

> Пользователь **сам** подписался на аккаунты и вступил в сообщества. Это его **явное действие** (explicit consent), а не скрытый анализ поведения. Фильтрация по подпискам — это то же самое, что email inbox: вы видите письма только от тех, кому дали свой адрес.

### Что НЕЛЬЗЯ делать в Natural Feed

| ❌ Запрещено | Почему |
|---|---|
| Показывать посты от тех, на кого пользователь НЕ подписан | Это «рекомендация» = профилирование |
| Учитывать интересы/поведение пользователя в Score | Это персонализация |
| Фильтровать по полу | Это профилирование (GDPR Art. 4(4)) |
| Менять Score в зависимости от того, КТО смотрит | Это персонализация |

| ✅ Допустимо (НЕ является профилированием) | Почему |
|---|---|
| Ранжировать по **системной популярности** (одинаковой для всех) | Не зависит от конкретного пользователя |
| Фильтровать по **подпискам** (явный выбор пользователя) | Explicit action, не анализ поведения |
| Фильтровать по **языку** (настройка пользователя) | Пользовательская настройка |
| **Anti-Flood Guard** (макс 3 бизнес-поста подряд) | Одинаковое правило для ВСЕХ |
| **New Content Slots** (каждый 10-й — свежий) | Одинаковое правило для ВСЕХ |

## 16. Таблицы БД

### Колонка `popularity_score` в таблице `posts`

```sql
-- Добавить колонку
ALTER TABLE posts ADD COLUMN popularity_score NUMERIC DEFAULT 0;

-- Функция пересчёта
CREATE OR REPLACE FUNCTION recalc_popularity_score(p_id UUID)
RETURNS VOID AS $$
DECLARE
  v_likes INT;
  v_comments INT;
  v_saves INT;
  v_shares INT;
  v_followers INT;
  v_hours NUMERIC;
  v_engagement NUMERIC;
  v_rate NUMERIC;
  v_decay NUMERIC;
BEGIN
  SELECT likes_count, comments_count, saves_count, shares_count,
         EXTRACT(EPOCH FROM (NOW() - created_at)) / 3600.0
  INTO v_likes, v_comments, v_saves, v_shares, v_hours
  FROM posts WHERE id = p_id;

  SELECT GREATEST(followers_count, 1)
  INTO v_followers
  FROM users WHERE id = (SELECT author_id FROM posts WHERE id = p_id);

  v_engagement := v_likes * 1.0 + v_comments * 2.0 + v_saves * 3.0 + v_shares * 2.5;
  v_rate := v_engagement / SQRT(v_followers::NUMERIC);
  v_decay := EXP(-0.693 * v_hours / 24.0);

  UPDATE posts SET popularity_score = v_rate * v_decay WHERE id = p_id;
END;
$$ LANGUAGE plpgsql;
```
